# 16 当たり具合の測り方

**この文書で決めること:** 学習に使っていないデータで、この予想の当たり具合をどう測るか。学習データ・検証データ・テストデータの期間をどう分けるか。何と比べれば「当たっている」と言えるか。予想を直したとき、直したものを採用してよいかを、どう確かめるか。

| 決めること | 結論 |
|---|---|
| 1. 期間の分け方 | 時期で分ける。既定は 学習 2021年8月〜2025年6月、検証 2025年7〜12月、テスト 2026年1月〜（穴馬の予想と同じ共通の既定）。`train` の引数で変えられる |
| 2. 評価指標 | 穴馬の予想で決めた共通の指標（ログ損失・AUC・Brier と、人気の基準との比べ方・同じ人気の中での AUC）を、時点ごとに LightGBM・CatBoost・平均の3行で出す |
| 3. 比べる基準 | 1番人気（`train` の出力）と、オッズだけで学習したモデル（研究「既存モデルの改善」の比べ方） |
| 4. 半年ずつずらした確かめ | 予想を直すときは、7つの半年の区切りで学習し直し、テスト期間のログ損失をオッズだけの基準と比べる。7つのうち 5つ以上で小さければ採用する |
| 5. ハイパーパラメータの調整のやり方 | 自動の探索はしない。設定ファイルを変えて `train --config` で学習し、2つの検証期間で初期値と比べる。両方で良ければ初期値を直す |
| 6. ◎ の単勝回収率の確かめ（期待度） | 1着のモデルの確率から単勝の期待値を出し、◎（期待値1位）の期待値でレースを 高・低 に分ける（線は 1.00 で固定）。採用の基準は、7つの区切りのテスト期間で、期待度「高」の ◎ の単勝回収率と 90% の幅の下の端が 100% を超えること。確かめた結果は基準を満たさず、◎ の単勝は買わない（確かめ中） |

用語の意味は [02-glossary.md](02-glossary.md) を参照。指標を計算するクラス（`MetricCalculator`・`ModelEvaluator`）は [04-classes.md の「evaluation/」](04-classes.md#evaluation--当たり具合を測るshared) にある。

## 1. 期間の分け方

**区分（ウォームアップ・学習・検証・テスト）の意味と既定の日は、穴馬の予想の [16 の「1. 期間の分け方」](../穴馬が3着以内に入るかを予想/16-evaluation.md#1-期間の分け方) と同じである。** どちらも共通の `TrainingPeriod`（`src/yosou/shared/dataset/training_period.py`）の既定を使う。区切りの日を変える引数は [08-training-data.md の「4. 期間の指定」](08-training-data.md#4-期間の指定)、学習データの始まりを 2021年8月にした理由は同じ節の「既定を 2021年8月からにした理由」を参照。

この予想で、実装で決まっていることは次のとおり。

| 決まり | 理由 |
|---|---|
| `PeriodSplitter` が、検証データの始まりとテストデータの始まりの2つの日で、学習データを3つに分ける。どれかが空なら止まる | 空の期間で学習や評価をすると、何も確かめないまま「学習できた」ように見えるため |
| `train` は、検証データだけで当たり具合を測る。テストデータは `train` では使わない | テストデータの結果を見て直すと、テストの結果に合わせて直してしまうため。テストデータは下の「4.」のような、最後の確かめに取っておく |
| 木を足すのを止める判断（早期終了）にも、検証データを使う | 学習データだけで木を足し続けると、学習データに合わせすぎる（過学習）ため（[12-lightgbm.md](12-lightgbm.md#2-ハイパーパラメータの初期値)・[13-catboost.md](13-catboost.md#2-ハイパーパラメータの初期値)） |

## 2. 評価指標

**指標の意味と良い向きは、穴馬の予想の [16 の「2. 評価指標」](../穴馬が3着以内に入るかを予想/16-evaluation.md#2-評価指標) と同じである。** どの予想も、共通の `MetricCalculator` で同じ指標を計算する。`train` の出力の「検証データでの当たり具合」と「人気の基準との比べ方」の2つの表に出る。

この予想での読み方は次のとおり。

| 表の列 | この予想では |
|---|---|
| 確率1位の馬の3着以内率 | 各レースで、モデルがいちばん高い確率を付けた馬（モデルの本命）が 3着以内に入った割合 |
| 確率1位の馬の複勝回収率 | モデルの本命の複勝を、全レースで 100円ずつ買ったときの回収率 |
| 人気最上位の馬の3着以内率・複勝回収率 | 各レースの1番人気で同じ値を出したもの。モデルによらない**基準**。本命の値がこれと同じなら、モデルは 1番人気をなぞっているだけである |
| 人気の中での AUC | 1番人気どうし、2番人気どうし…で比べた AUC を、頭数で重み付けして平均したもの。0.5 より大きいほど、人気で分からないところを当てている |

**モデルの行は、時点ごとに3行出る。** LightGBM・CatBoost・平均（アンサンブル）である。予測に使うのは平均なので、判断は平均の行で行う。平均の行が、2つのモデルのどちらよりもはっきり悪いときは、平均のしかた（[03-library-basics.md の 6.](03-library-basics.md#6-2つの予測確率を合わせる)）を見直す。

## 3. 比べる基準

| 基準 | 何を出すか | どこで比べるか | 何が分かるか |
|---|---|---|---|
| 1番人気 | 各レースの1番人気を選ぶ | `train` の出力（上の「人気最上位の馬」） | 1頭選ぶ使い方で、市場の本命より当たるか |
| オッズだけで学習したモデル | 特徴量を、オッズから出した値（単勝オッズ・人気順位・オッズから見た勝率・オッズから見た3着以内率）と出走頭数だけにして、同じ手順（オッズから作った基準を出発点にする）で学習したモデル | 下の「4.」（研究「既存モデルの改善」の比べ方。`train` の出力には無い） | 近走・適性・調教・血統などの馬の情報が、オッズで分かること以上を足しているか |

## 4. 半年ずつずらした確かめ

`train` の既定の分け方では、検証データは半年1つだけである。半年1つの結果には偶然の幅があるので、**特徴量を足す・学習データの分け方を変えるなど、予想そのものを直すときは、過去で学習して次の半年を予想する確かめ（ウォークフォワード）を、7つの区切りで行う。** 仕組みは研究「既存モデルの改善」（`research/既存モデルの改善/`）にあり、予想のパッケージの `dataset_builder` と、共通の LightGBM・CatBoost のクラスをそのまま使う。

| 区切り | 学習 | 検証 | テスト |
|---|---|---|---|
| 2023年前半 | 2017年1月〜2022年6月 | 2022年7〜12月 | 2023年1〜6月 |
| 2023年後半 | 2017年1月〜2022年12月 | 2023年1〜6月 | 2023年7〜12月 |
| 2024年前半 | 2017年1月〜2023年6月 | 2023年7〜12月 | 2024年1〜6月 |
| 2024年後半 | 2017年1月〜2023年12月 | 2024年1〜6月 | 2024年7〜12月 |
| 2025年前半 | 2017年1月〜2024年6月 | 2024年7〜12月 | 2025年1〜6月 |
| 2025年後半 | 2017年1月〜2024年12月 | 2025年1〜6月 | 2025年7〜12月 |
| 2026年 | 2017年1月〜2025年6月 | 2025年7〜12月 | 2026年1月〜（DB にある最後の日まで） |

- 区切りは `research/既存モデルの改善/analysis/windows/test_windows.py` の `WINDOWS` にある。学習の始まりは、研究の学習データの表の始まり（2017年1月）にそろえてある。`train` の既定（2021年8月）とは違う。
- 時点は当日、ハイパーパラメータは初期値のままで、LightGBM と CatBoost の両方を学習し、確率を平均する。
- 検証期間は、木を足すのを止める判断にだけ使う。テスト期間の結果は、どの線を決めるのにも使わない。
- 測るのは、テスト期間のログ損失と人気の中での AUC、複勝を期待値で買ったときの回収率（開催日を単位にしたブートストラップの 90% の幅を添える）である。

**採用の基準。** テスト期間のログ損失が、上の「オッズだけで学習したモデル」より小さい区切りが 7つのうち 5つ以上あり、全期間を合わせても小さいこと。材料を1つずつ足す実験も、同じ基準で、直した後の予想（研究の「変更版」）と比べる。

動かし方（リポジトリ直下で。数値は Git の対象外の `reports/既存モデルの改善/` に出る）:

```powershell
uv run python research/既存モデルの改善/build_tables.py                              # 学習データの表を作る（数分）
uv run python research/既存モデルの改善/walk_forward.py --model form_aptitude_top3   # 7つの区切りで学習し、予測を残す（40分ほど）
uv run python research/既存モデルの改善/compare.py                                   # 比べ方の表を出す
```

（1行目は、4つの予想の学習データを全期間ぶん作って保存するコマンド。2行目は、この予想を区切りごとに学習し直して、検証とテストの予測を残すコマンド。3行目は、直す前・オッズだけ・直した後を並べた表を `reports/既存モデルの改善/compare/form_aptitude_top3.md` に出すコマンド）

研究「一番人気を疑う」の直し方を移したときも、この区切りと基準で時点ごとに今の予想と比べ、木曜・前日・当日の全部で採用した（[15-decisions.md の 11](15-decisions.md#11-研究一番人気を疑うの直し方を移す)。動かし方は研究の `port_check.py`。比べる相手は「オッズだけ」ではなく今の予想で、時点は木曜・前日・当日のそれぞれ）。

この確かめで直した後の予想を採用した。結果は [15-decisions.md の 7](15-decisions.md#7-既存モデルの修正計画での直し)、表の読み方は研究の [02-結果の読み方.md](../../../research/既存モデルの改善/docs/02-結果の読み方.md) を参照。

## 5. ハイパーパラメータの調整のやり方

ハイパーパラメータ（木の数の上限・葉の数など。初期値は [12-lightgbm.md](12-lightgbm.md#2-ハイパーパラメータの初期値)・[13-catboost.md](13-catboost.md#2-ハイパーパラメータの初期値)）は、次の手順で変える。グリッドサーチのような自動の探索は作らない。

1. 変えたい項目だけを書いた設定ファイルを作る（書き方は [14-hyperparameter-settings.md](14-hyperparameter-settings.md)）。
2. `train --config <設定ファイル>` で学習し、「検証データでの当たり具合」の平均の行（ログ損失・AUC）を、初期値で学習したときと比べる。`--models` で別の置き場所を指定し、本番のモデルを上書きしない。
3. 検証期間をもう1つ変えて（`--valid-from 2025-01-01 --test-from 2025-07-01` で 2025年1〜6月）、同じ比べ方をする。
4. 2つの検証期間の両方で良くなったときだけ、初期値のファイル（`src/yosou/form_aptitude_top3/setting/default_settings.toml`）を直す。

```powershell
uv run python -m yosou.form_aptitude_top3 train --config 試す設定.toml --models reports/近走と適性から3着以内を予想/models-試し
uv run python -m yosou.form_aptitude_top3 train --config 試す設定.toml --models reports/近走と適性から3着以内を予想/models-試し --valid-from 2025-01-01 --test-from 2025-07-01
```

（1行目は、試す設定で学習し、既定の検証期間（2025年7〜12月）で当たり具合を出すコマンド。2行目は、検証期間を 2025年1〜6月に変えて同じことをするコマンド。どちらも本番のモデルとは別の置き場所に書く）

- 2つの検証期間で比べるのは、半年1つの差が偶然かどうかを見分けるためである。学習データの始まり（[08-training-data.md](08-training-data.md#既定を-2021年8月からにした理由)）と LightGBM の `min_category_count`（[12-lightgbm.md](12-lightgbm.md#2000-にした理由)）も、この比べ方で決めた。
- 上の「4.」の確かめ（研究の `walk_forward.py`）は、ハイパーパラメータを初期値のまま使う。設定ファイルは受け取らない。

## 6. ◎ の単勝回収率の確かめ（期待度）

[15-decisions.md の 14](15-decisions.md#14-1着のモデルを足して--を単勝の期待値で選ぶ) で決めた「1着のモデルと、単勝の期待値で選ぶ ◎」の当たり具合を、次の決まりで測る。
1着のモデルそのものの確率の誤差（ログ損失・AUC）は、上の 2. と同じ指標を「1着」の目的変数で出す（`train` の出力に「1着」の行が増える）。

### 単勝の期待値と ◎

```text
単勝の期待値 = 1着になる確率 × 単勝オッズ        （1 で元返し。前日・当日だけ）
◎           = 消（危険な人気馬）を除いて、単勝の期待値がいちばん高い馬（全レースに1頭）
```

### 期待度（レースごとの2段階）

| 期待度 | ◎ の単勝の期待値 | 意味 |
|---|---|---|
| 高 | 1.00 以上 | モデルは単勝を買って得と見ている。単勝を買う候補 |
| 低 | 1.00 未満 | モデル自身が損と見ている。◎ は付くが、単勝は買わない |

線は 1.00 で固定し、予測では ◎ の期待値からそのまま決める（`ExpectationLevel`。[04-classes.md](04-classes.md#place_valuewin_value--期待値shared)）。
木曜はオッズが無く期待値が出ないので、期待度も無い。

**線を検証データで決めない理由。** はじめは「高」の線を区切りごとに検証期間で決める形（候補 1.00〜2.00 から、（回収率 − 1）× √頭数 がいちばん大きい線）で確かめた。
7つの区切りで線は 1.05〜1.65 とばらつき、3つの区切りでは線が決まらず（検証期間の半年に、単勝回収率が 100% を超える線が無い）、「高」のレースは全体の 3.5% しか無く、
2025年以降は1レースも出なかった。半年の検証期間では ◎ の数が線を決めるのに足りない。そのため、線は固定にした（利用者の決定）。

### 採用の基準（結果を見る前に決めた）

| 項目 | 中身 |
|---|---|
| 期間 | 上の 4. の7つの区切りのテスト期間（2023年1月〜2026年9月） |
| 時点 | 今の本番の前日のモデルと同じ材料で判定する（木曜はオッズが無いので期待値が出ない。当日も同じ表を出す） |
| 測るもの | 期待度ごと（高・低）の ◎ の単勝の成績7つと、単勝回収率の 90% の幅（開催日を単位にしたブートストラップ）、レース数と 1開催日あたりのレース数、年ごとの単勝回収率 |
| 採用の基準 | **期待度「高」の ◎ の単勝回収率が 100% を超え、90% の幅の下の端も 100% を超える** |
| 満たさなかったとき | 「届いたが偶然と区別できない」か「届かなかった」をそのまま書く。◎ の決め方と1着のモデルは残し（◎ 全体の成績が今より悪くなっていなければ）、期待度「高」を単勝を買う根拠にはしない |

- 確定オッズでの検証なので、実際に買うとき（締め切り前のオッズ）より良く出る。結果に書き添える。
- 道具は `tools/印の成績/mark_stats.py --win <1着の予測>`。1着の予測は、研究「既存モデルの改善」の入口⑪（`win_check.py`）で作る。

### 確かめた結果

数値は Git の対象外の `reports/印の成績/h2h_ability_h2h-day_before.md`（表1・表6）にある。前日のモデルと同じ材料で、1着のモデルを7つの区切りで学んで確かめた。

| 見たこと | 結果 |
|---|---|
| 1着のモデルの確率の誤差 | 7つすべての区切りで、オッズから見た勝率をそのまま使うより小さい。確率も帯ごとに実際の勝率とよく合っている |
| ◎ 全体の単勝回収率 | 3着以内の確率の1位で選んでいたときより上がり、同じ人気の馬全体を控除率と同じくらいの幅で上回る。ただし 100% には届かず、90% の幅は 100% をまたぐ |
| 期待度「高」（期待値 1.00 以上）の ◎ | 全レースの4割弱（1開催日に 10レースほど）。単勝回収率は 100% を少し超えるが、90% の幅は 100% をまたぎ、年ごとに大きく振れる。**採用の基準は満たさない（届いたが偶然と区別できない）** |
| 期待度「低」の ◎ | 単勝回収率は 100% に届かないが、同じ人気の馬全体は上回る |
| 期待値の高い帯 | 期待値の高い ◎ は大穴ばかりで、当たりが数十回しか無く、成績は運で大きく振れる。期待値の高い順に絞っても、市場との差（上乗せ）は増えず、ばらつきが増えるだけだった |

**判断。** ◎ の決め方（単勝の期待値の1位）と期待度は本番に入れる（印と画面に出す）。◎ の単勝は、基準を満たすまでは買わない（[買うレースと買い目を決める の 08 の 2](../買うレースと買い目を決める/08-bankroll-and-review.md#2-勝負レースの中の掛け金)）。
これからのレースの確定成績がたまったら、同じ道具で確かめ直す。100% を自信を持って超えるには、1着のモデルの上乗せ（市場との差）そのものを増やす必要がある。

## 今はしないこと

| しないこと | 理由と、代わりにすること |
|---|---|
| 特徴量の重要度を `train` の出力に出す | 当たり具合の判断には使わないので出さない。似た列が多いと重要度が割れて、効き目を正しく表さないためである。見たいときは、保存したモデルから LightGBM の `feature_importances_`、CatBoost の `get_feature_importance()` で読む（[03-library-basics.md の 4.・5.](03-library-basics.md#4-lightgbm-の使い方)） |
| 学習し直す間隔を決める | 決めていない。利用者が `train` を実行したときに学習し直す。上の「4.」は半年ごとに学習し直して確かめたので、半年を目安にする |
| 複勝を買う線（期待値がいくつ以上なら買うか）を、この設計書に入れる | 入れない。この予想は、予測の表に複勝の期待値を出すところまでを受け持つ。買う線は、買い方の設計書（[買うレースと買い目を決める の 07](../買うレースと買い目を決める/07-expected-value.md#買う線)）で扱う |

## 決めたこと
