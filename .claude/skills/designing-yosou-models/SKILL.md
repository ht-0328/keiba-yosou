# 予想AIの設計書を書く

## 使う場面

新しい予想（予想AI）を作ってと頼まれ、プログラムを作る前の設計書を書くとき。流れと利用者への確認は、エージェント `yosou-model-design-orchestrator` が持つ。このスキルは、各手順の具体的なやり方を持つ。

**手本は `docs/design/近走と適性から3着以内を予想/` の 01〜15 である。** 書く前に、同じ番号の手本を開き、何をどこまで決めているかを見る。手本の中身（特徴量の表など）は写さず、この予想に合わせて書く。

| 資料 | 何が書いてあるか | いつ読むか |
|---|---|---|
| [references/document-set.md](references/document-set.md) | 01〜15 のそれぞれに書くことと、手本の場所 | 手順2〜5 で、各文書を書く前 |
| [references/writing-rules.md](references/writing-rules.md) | 書き方の規則（利用者から受けた指摘をまとめたもの） | 書き始める前に一度通して読み、書きながら開いておく |
| [scripts/check_links.py](scripts/check_links.py) | 設計書どうしのリンク（ファイルと節）が実在するかの検査 | 手順6 |

## 手順

写して、終わったものに印を付ける。

```text
- [ ] 手順1: 依頼を、予想のやり方に言い直す
- [ ] 手順2: 概要と用語の文書を書く（01・02）
- [ ] 手順3: 道具・クラス・図の文書を書く（03〜06）
- [ ] 手順4: 時点・学習データ・特徴量・目的変数・リークの文書を書く（07〜11）
- [ ] 手順5: モデルごとの設計・設定・決めてほしいことの文書を書く（12〜15）
- [ ] 手順6: 検査する
- [ ] 手順7: 決まったことを反映する
```

### 手順1 依頼を、予想のやり方に言い直す

「危険な人気馬を見つける」のような依頼は、そのままでは目的変数にならない。次の3つを決めて、確認1に出す。

| 決めること | 例（危険な人気馬） |
|---|---|
| 何を当てるか（目的変数の定義） | 1〜3番人気の馬が 4着以下なら 1、3着以内なら 0。対象の行は 1〜3番人気の馬だけ |
| 何を材料にするか（予想のやり方） | 近走・適性・調教から、人気のわりに走らない馬を見つける |
| 設計書のフォルダ名 | `docs/design/人気馬が4着以下になるかを予想/`（道具の名前でなく、予想のやり方が分かる日本語） |

- **DB を見るときは、SQL を組み立てる前に `tools/README.md` の早見表の道具を使う。** 対象の事象は、`tools/人気馬が負けたレース/`・`tools/穴馬が勝ったレース/` などで事例と件数を確かめられる。
- 人気・オッズを対象の行を選ぶ条件に使うときは、どの時点の人気か（確定か、締め切り前か）を書く。確定の人気は、レース前には分からない。
- 選び方が複数あるときは、おすすめを1つ決め、ほかの選び方で何が変わるかを並べる。

### 手順2 概要と用語の文書を書く（01・02）

[references/document-set.md](references/document-set.md) の 01・02 を読んで書く。01 の冒頭の一文は「〇〇から、〇〇を出す予想である」の形にする。架空の1頭の例を入れる。

### 手順3 道具・クラス・図の文書を書く（03〜06）

- **03（道具の使い方）**: 手本と同じ道具（LightGBM・CatBoost・pandas）を使うなら、手本の 03 へのリンクと、この予想で違う点だけを書く。新しい道具を使うなら、コードを載せる前に動かして確かめる（下の「コードを動かして確かめる」）。
- **04（クラスとパッケージ）**: 流れを進めるクラス（Workflow）と、仕事ごとのクラスを決める。パッケージは `src/yosou/<予想のやり方が分かる英語>/` の下に置く。
- **05・06（図）**: 04 のクラス名とメソッド名で描く。図の使い分けは 01 に書いた方針に従う。

**コードを動かして確かめる。** JV-Data ではなく乱数の架空データで、スクラッチパッド（作業用のフォルダ）に置いたスクリプトを次の形で動かす。確かめた版を文書に書く。

```bash
uv run --no-project --with lightgbm --with catboost --with pandas --with scikit-learn python <スクリプト>
```

（使うライブラリを一時的に入れて、スクリプトを動かすコマンド。`uv` が PATH に無ければ `CLAUDE.md` に書いてある場所の `uv.exe` を使う）

### 手順4 時点・学習データ・特徴量・目的変数・リークの文書を書く（07〜11）

[references/document-set.md](references/document-set.md) の 07〜11 を読んで書く。

- **使うデータの期間は、DB に今入っている期間ではなく、JRA-VAN が提供している期間で判断する。** 提供開始は `../jvdata-store/docs/03-dataspecs.md` の表にある。DB に足りなければ、jvdata-store で取得する前提で設計し、足りないことを 15 か 05 の「これから作るところ」に書く。
- 特徴量の例の値は、01 の「1頭の例」と同じ架空の馬にそろえる。

### 手順5 モデルごとの設計・設定・決めてほしいことの文書を書く（12〜15）

LightGBM と CatBoost は、別の文書（12・13）に分ける。同じ節に2つを混ぜて書かない。15 には、この予想で利用者に決めてほしいことを集める（[references/document-set.md](references/document-set.md) の 15）。

### 手順6 検査する

設計書のフォルダで、リンク先のファイルと節が実在するかを確かめる。

```bash
uv run --no-project python .claude/skills/designing-yosou-models/scripts/check_links.py "docs/design/<予想のやり方>"
```

（設計書どうしのリンクと、`#` で指した節の見出しが実在するかを、GitHub と同じ規則で確かめるコマンド）

「問題 0 件」になるまで直す。あわせて、次を目で確かめる。

- 同じ事実（数・期間・決定）が、2つの文書に書かれていない。
- 「この文書で決めること」が、どの文書の冒頭にもある。
- JV-Data の実値が載っていない。例の値は架空である。

### 手順7 決まったことを反映する

利用者が決めたら、15 を「決めたこと」に変える（選ばなかった選び方は残す）。決まった内容に合わせて関係する文書を直し、各文書の「決めてほしいこと」の節を消す。01 の「状態」を直す。手順6 の検査をもう一度通す。
