# 設計書の書き方の規則

最初の予想（`docs/design/近走と適性から3着以内を予想/`）を設計したときに、利用者から受けた指摘をまとめたもの。どれも「なぜそうするか」を添えてある。迷ったら理由に立ち返る。

## 目次

- 文書の組み立て
- 言葉
- 名前
- 図
- プログラムの部品
- 道具の説明
- データ
- 説明の短さ

## 文書の組み立て

| 規則 | 理由（受けた指摘） |
|---|---|
| 各文書は「この文書で決めること」から始め、結論をその答えとして書く | 結論から入ると「何の結論かが分からん」 |
| 1つの話題は1つの文書にだけ書き、ほかからは「〇〇.md の「見出し」を参照」とリンクする | 同じことが2か所にあると、同じ意味か違う意味かを読み手が確かめる手間が出る。片方だけ直すと食い違う |
| ファイル名と題名に、読む順の番号を付ける | 番号が無いと「読む順番わからん」 |
| 決めてほしいことは 15 に集め、関連する資料の節へリンクする | 散らばっていると、何を決めればよいかが分からない |
| 設計書は `docs/design/<予想のやり方>/` に、1つの予想で1つのフォルダにまとめる | 利用者の指定 |

## 言葉

| 規則 | 理由（受けた指摘） |
|---|---|
| 機械学習で普通に使う用語（特徴量・目的変数・リーク・過学習など）をそのまま使い、02 で意味を説明する | 独自の言い換え（「材料の列」「カンニング」）は、ほかの資料を読むときに通じない |
| いくつかのものをひとまとめにする言葉（「処理」「参加者」「部品」「仕事」）を作らない。中身を具体的に並べる | 「処理とは？」「参加者がなにをさしてんのかわからん」「言葉変えただけで全然いみわかんない」 |
| プログラマーが普段使う言葉にする（「公開関数」ではなく「public メソッド」） | 「公開関数なんてふつういうか？」 |
| 見出しは、それだけで何の節か分かる言い方にする（「言葉」ではなく「用語の意味」） | 「言葉って見出しが意味わからん」 |

## 名前

| 規則 | 理由（受けた指摘） |
|---|---|
| フォルダ名・パッケージ名は、使う道具ではなく予想のやり方が分かる名前にする（フォルダは日本語、パッケージは英語） | 「gbdt って何」「ツールの話じゃなくて具体的な予想理論が分かる名前にしなさい」 |
| 題名にも、何をする文書かが分かる言葉を入れる（「LightGBM のモデル設計」ではなく「LightGBM で学習・予測するための設計」） | 「これは何をしたいの？」 |
| クラス名に `Manager`・`Processor` のような何でも入る名前を付けない | 関係の無い仕事が足されていく（software-engineering-guide の DS-13） |

## 図

図は2種類だけ使い、方針を 01 に書く。

| 図 | 表すこと | 記号がコードの何に当たるか |
|---|---|---|
| シーケンス図 | 利用者・jvdata-store・元DB と、この AI のクラスの間で、どのメソッドを、どの順に呼び、何を渡して何が返るか | 縦の線1本 = クラス1つ。実線の矢印1本 = 呼び出し1回（public メソッド1回・SQL 1回・`fit` 1回）。点線 = その戻り値 |
| フローチャート | 1つの public メソッドの中で、if 文によってどちらに進むか | 図1枚 = public メソッド1つの中。ひし形1つ = if 文1つ |

- 同じ手順を両方の図で描かない（「シーケンスとフローチャートを分けろ」「どういう理由で使い分けてるのかわからない」）。
- 分かれ道の無い一続きの作業は、シーケンス図の自分に戻る矢印で書く。引数のチェックのような、どのメソッドにもある作業は描かない。
- くり返しは `loop`、利用者の手順の違いは `opt` の枠で描く。メソッドの中の if 文に `opt` を使わない。
- 凡例（図の読み方）は、シーケンス図は 05、フローチャートは 06 にだけ書き、ほかは参照する。
- 図は Mermaid で書く。VS Code で見るには拡張機能 `bierner.markdown-mermaid` が要ることを 01 に書く。

## プログラムの部品

| 規則 | 理由（受けた指摘） |
|---|---|
| 部品は、コードの単位（クラス・public メソッド・モジュール・パッケージ）で決める | 「1つの if 文のことをいってるの？メソッドのこと？…ちゃんと定義しなさい」 |
| 流れを進める（オーケストレーションする）クラスを明示し、受け渡すだけにする | 「各クラスをオーケストレーションするのはどのクラスにするのか」 |
| パッケージ構成まで決める。仕事の領域で分け、参照を一方向にする | 「クラスを配置するパッケージ構成まで考えて」。software-engineering-guide の DS-08〜DS-11 |
| LightGBM と CatBoost は、別の文書・別のクラスに分け、同じインターフェースを守らせる | 「LightGBM と CatBoost は設計をわけろ」。利用者は両方を使うことを求めている（片方に絞る提案をしない） |
| ハイパーパラメータは、設定ファイルで外から指定できるようにする | 「木の数とか、ハイパーパラメータは外部から指定できるようにしてほしい」 |
| 予測は、木曜・前日・当日の3つの時点で出せるようにし、時点ごとに別のモデルを学習する | 「いつ予測するかは3つの時点それぞれで出せるようにしてほしい」（手本で決めたこと。新しい予想でも既定にし、違うなら 15 で聞く） |

## 道具の説明

| 規則 | 理由（受けた指摘） |
|---|---|
| 設計の前に、使う道具で何ができるかの入門（03）を置く。補助の道具（pandas など）も含める | 「LightGBM と CatBoost の使い方をそもそも知らん」「pandas がわからん」 |
| コード例は、載せる前に架空のデータで動かして確かめる | 動かして初めて分かることがある（例: `LGBMClassifier` には scikit-learn が要る、lightgbm 4.7.0 では `eval_set=` が非推奨） |
| ライブラリの約束に従うための行は、「何をどうするか（理由を一言）」と「変換前 → 変換後の小さな表」だけを添える | 表・エラーの文面・別のやり方の理由まで並べたところ「だらだら説明書いてるけど、シンプルに文字列からこういう型にします、としめしてほしい」 |
| 例のために値を絞っているところは、なぜその値かと本番ではどうなるかを、コメントに一言で書く | 「まずなんで二つだけなの」 |

## データ

| 規則 | 理由（受けた指摘） |
|---|---|
| 使えるデータの期間は、DB に今入っている期間ではなく、JRA-VAN が提供している期間で判断する | 「DB に 2025年からしかない」を理由に外したところ「実際はそれよりも前のものもあるみたいなので、方針を直せ」 |
| DB を見るときは、SQL を組み立てる前に `tools/` の道具を使う | keiba-yosou の決まり（`CLAUDE.md`） |
| JV-Data の実値（馬名・騎手名・オッズ・払戻・成績の値）を設計書に書かない。例は架空の値にする。件数の数え上げは書いてよい | keiba-yosou は公開リポジトリである |
| 予測の時点で分からない情報（そのレースの結果、確定オッズ、今日時点のマスタの累計）を特徴量にしない | リーク。学習では当たるのに本番で当たらなくなる |

## 説明の短さ

| 規則 | 理由（受けた指摘） |
|---|---|
| 「何をしているの」には、目的と理由を一言で答える | 「シンプルに LightGBM は文字列を扱えないからカテゴリーに変換してますといってほしい」 |
| 表は2〜4列にし、説明の列は短くする。確かめた事実でも、全部は並べない | 長い説明は読まれない |
